## Implementación

1. **Catálogos y contrato**
   - Publicar catálogos de solo lectura: sedes, estados de cita, roles, regímenes y planes activos.
   - Extender el registro con `insurancePlanId` opcional. La API validará que el plan exista y esté activo, y creará la afiliación inicial sin afectar el flujo cuando se omita.
   - Documentar el contrato REST, errores `400`, `401`, `403`, `404`, `409`, autorización y compatibilidad entre ambos repositorios.
   - Usar fecha y hora local de `America/Bogota`; los contratos de agenda usarán fecha `YYYY-MM-DD` y hora `HH:mm`.

2. **Oferta administrable**
   - ADMIN gestiona especialidades, con duración limitada a 30 o 60 minutos, estado activo y baja lógica.
   - ADMIN crea profesionales con datos sintéticos, código profesional, matrícula ficticia y contraseña temporal. La contraseña se recibe solo en la solicitud, se hashea y nunca se devuelve ni registra.
   - ADMIN asigna una o varias especialidades, una primaria y una o ambas sedes; también activa o desactiva profesionales.
   - API propuesta:
     - `GET /api/v1/catalogs/...`
     - `GET|POST|PATCH /api/v1/admin/specialties`
     - `POST /api/v1/admin/professionals`
     - `PUT /api/v1/admin/professionals/{id}/specialties`
     - `PUT /api/v1/admin/professionals/{id}/locations`
     - `PATCH /api/v1/admin/professionals/{id}/active`

3. **Disponibilidad**
   - PROFESSIONAL crea, consulta, edita y elimina bloques futuros propios.
   - Cada bloque exige profesional activo, sede asignada, inicio y fin válidos en límites de 30 minutos, fecha futura y ausencia de solapamiento.
   - Al crear o modificar un bloque se generan slots atómicos de 30 minutos.
   - Un bloque con slots comprometidos no puede editarse ni eliminarse.
   - API propuesta:
     - `GET|POST /api/v1/professional/availability-blocks`
     - `PATCH|DELETE /api/v1/professional/availability-blocks/{id}`
     - `GET /api/v1/professional/availability-blocks?date=&locationId=`

4. **Búsqueda y reserva**
   - USER consulta disponibilidad por sede, especialidad, profesional y fecha. La API deriva el tipo general o especializado desde la especialidad elegida.
   - La disponibilidad solo mostrará profesionales activos, asociados a la especialidad y habilitados en la sede.
   - Una especialidad de 60 minutos exige dos slots consecutivos libres.
   - `POST /api/v1/appointments` recibirá `professionalId`, `locationId`, `specialtyId`, `startAt` y motivo opcional.
   - La reserva se procesará dentro de una transacción con bloqueo de los slots solicitados:
     - medicina general crea cita `APPROVED`, asigna slots y registra historial con fuente `SYSTEM`;
     - especialidad crea cita `REQUESTED`, retiene slots y registra historial con fuente `USER`;
     - si uno de los slots ya está tomado o la selección dejó de ser válida, responde `409 Conflict`.
   - ADMIN obtiene únicamente solicitudes especializadas pendientes y decide:
     - `POST /api/v1/admin/appointments/{id}/decision`
     - `APPROVE`: conserva slots y cambia a `APPROVED`;
     - `REJECT`: exige motivo, libera slots y cambia a `REJECTED`.
   - La consulta administrativa de S3 se limita a solicitudes especializadas `REQUESTED`; la bandeja con reprogramaciones y filtros completos queda para HU-031.

5. **Frontend sin mocks**
   - Eliminar `mockData.ts`, citas de `localStorage`, profesionales simulados, especialidades ficticias, tarifas, calificaciones, videollamadas, recetas y cualquier dato no soportado por el PRD.
   - Conservar estructura visual, colores, tipografía, espaciado, tarjetas, modal y jerarquía visual del prototipo Stitch.
   - Reemplazar los pasos del modal por datos reales:
     1. especialidad y sede;
     2. profesional disponible;
     3. fecha y slots disponibles;
     4. motivo y confirmación.
   - Mostrar el resultado real de la reserva: `APPROVED` para general y `REQUESTED` para especializada.
   - Mientras HU-025 no exista, no se mostrará una lista simulada de “Mis citas”; tras la reserva solo se presentará una confirmación basada en la respuesta de API.
   - Agregar vistas con el mismo sistema visual para:
     - ADMIN: especialidades, profesionales, asignaciones y decisiones pendientes;
     - PROFESSIONAL: bloques y calendario propio.
   - Aplicar rutas y acciones por rol, estados de carga, vacío, error, éxito y acceso denegado.

1. Crea una prueba que intente dos reservas sobre los mismos slots.

1. Revisa que la reserva general quede APPROVED.

- PASS si existe una única reserva válida, la segunda devuelve 409 y las pruebas pasan.

# S5 — Estado integrado, Swagger y webhook inicial de n8n Cloud

## Resumen

## Cambios

- Validar primero el reinicio de Docker y registrar en `current-state.md` las ramas, commits, contenedores, servicios, pruebas y funcionalidades verificadas.
- Documentar acceso local:
  - Frontend Vite: `http://localhost:5173`.
  - API: `http://localhost:8080`.
  - Swagger UI: `http://localhost:8080/swagger-ui/index.html`.
  - OpenAPI JSON: `http://localhost:8080/v3/api-docs`.
  - MySQL mediante `docker compose exec`; incluir consultas de solo lectura para verificar usuarios, citas e historial sin imprimir credenciales ni datos personales.
- Añadir `springdoc-openapi-starter-webmvc-ui` versión `2.8.13`, compatible con Spring Boot 3.5 según la [matriz oficial de springdoc](https://springdoc.org/v2/).
- Configurar metadatos OpenAPI, esquema JWT Bearer y documentación de rutas, roles, respuestas y errores. Autorizar solamente `/swagger-ui/**` y `/v3/api-docs/**` como documentación pública; las operaciones siguen requiriendo autenticación.
- Implementar un adaptador de eventos HTTP activable por configuración:
  - Variables: `N8N_WEBHOOK_ENABLED`, `N8N_WEBHOOK_URL`, `N8N_WEBHOOK_BEARER_TOKEN`.
  - Desactivado por defecto; si se activa sin URL o token, el backend fallará al iniciar con un error de configuración.
  - Enviará `Authorization: Bearer <token>` a n8n Cloud.
  - El payload mínimo será: `schemaVersion`, `eventId`, `eventType`, `appointmentId`, `status`, `source` y `occurredAt`. No incluirá datos personales ni credenciales.
  - Emitirá solo decisiones administrativas `APPROVED` y `REJECTED`, más cancelaciones de usuario `CANCELLED`. La aprobación automática de medicina general no generará webhook.
  - La llamada ocurrirá después del commit. Si n8n falla o no responde 2xx, la cita conservará su cambio; se registrará un log técnico sin secretos ni datos personales. Esta primera integración no tendrá reintentos persistentes.
- Configurar en n8n Cloud un flujo con **On Webhook Call**, Header Auth para el Bearer compartido y respuesta inmediata `200`. Las credenciales quedarán exclusivamente en n8n Cloud y en el archivo local no versionado.
- Registrar el contrato, la configuración requerida, la limitación de entrega sin reintentos y la evidencia de validación en Wiki, trazabilidad Scrum e historial de validación. No se implementará MCP en esta sesión.
